## Step 6：スキルを入れる（AI秘書スキルパック ＋ 自作）

毎日くり返す仕事のスキルは、ゼロから作らずに **AI秘書スキルパック**（DAIJOBU株式会社が提供。スキル15本＋調査係エージェント1体）をまとめて入れる。入れたら役割のおすすめから数本を試し、パックに無い自社独自の仕事だけを自作で足す。

### 6-1. パックを入れる

パックは、AI秘書ビルダーの「② 能力」でダウンロードした `第2部_能力_セット.zip` に入っている。展開すると次の形になっている。

```
ai-secretary-part2/
├── part2-setup.md     ← 本書（第2部の手順）＋ビルダーで選んだ内容
├── skills/            ← スキル15本（1本＝1フォルダ。SKILL.md と参考資料）
└── agents/
    └── researcher.md  ← 調査係エージェント
```

あなた（Claude Code）は、次の順で入れる。

1. **zip を展開する**（Mac は `unzip`、Windows は `tar -xf` か `Expand-Archive`）。展開先は、ダウンロードフォルダなど AI秘書のフォルダの外にする（中に展開すると、コピーしたあとも同じスキルの控えがフォルダに残って紛らわしい）。zip の場所が分からなければユーザーに聞く（ふつうはダウンロードフォルダにある）
2. **同じ名前のスキル・コマンドが既にないか確かめる**。[00 はじめに](<【ふぇね作成】Claude Code構築指示書.md>)の最短ルートで作った `.claude/commands/daily-schedule.md` などが残っていると、パック版と名前がぶつかる。見つけたらユーザーに一覧を見せて了承を取り、`.claude/_archive/` へ移す（消さない）。旧版に自社独自の工夫があれば、パック版の該当箇所か Gotchas（過去の失敗を1行で残す欄。書き方は 6-4）に書き写す
3. **コピーする**: 展開した `ai-secretary-part2/skills/` の中の15フォルダを AI秘書のフォルダ（`CLAUDE.md` があるフォルダ）の `.claude/skills/` へ、`ai-secretary-part2/agents/researcher.md` を `.claude/agents/` へ
4. **入ったことを確かめる**: `.claude/skills/` にパックの15フォルダ（`daily-schedule` など）が、`.claude/agents/` に `researcher.md` があることをユーザーに見せる。そのうえでユーザーに `/` を打ってもらい、スキルが候補に出てこなければ Claude Code を開き直してもらう
5. **「おはよう」の動きを確かめる**: パックの `/daily-schedule` は「今日の工程表をつくって」のような言葉で動く。第1部で `CLAUDE.md` に「『おはよう』→ `/daily-schedule`」を書いていれば、パック版も同じ名前なのでそのまま動く。書いていなければ、「おはよう」でも工程表を出したいかユーザーに聞き、出したいなら `CLAUDE.md` にその1行を足す

> **プラグインで入れる方法もある**: zip からコピーするかわりに、スキルパックをプラグインとして入れてもよい。その場合は、ユーザーに Claude Code（デスクトップアプリの Code タブ、またはターミナル）で次の2行を順に入力してもらう（スキルパックのリポジトリ `DAIJOBU-INC/ai-secretary-skills` の README「入れ方」と同じ手順）。
>
> ```
> /plugin marketplace add https://github.com/DAIJOBU-INC/ai-secretary-skills.git
> /plugin install ai-secretary@daijobu
> ```
>
> - **更新を受け取る**: `/plugin` の画面（Marketplaces）で `daijobu` の自動更新をオンにしておくと、スキルが直されたときに自動で届く。オフのままなら、同じ画面から手動で更新する
> - **zip とプラグインの両方は入れない**: プラグインで入れた場合は、手順3のコピーはしない（両方入れると、同じスキルが2つずつ並んでしまう）
> - **呼び名**: 名前を指定して呼ぶときは `/ai-secretary:daily-schedule` のように書く（`CLAUDE.md` の「おはよう」の行も、この名前に合わせる）

### 6-2. 役割のおすすめから試す

**ビルダーで選んだ「まず試す」（全員の土台の `/daily-schedule`・`/mtg-prep` ＋役割のおすすめ）を、上から1本ずつ実際に頼んで動かす。** 入れた15本はすべて使えるが、最初から全部は試さない。頼み方は、下の一覧の「こう頼む」のような自然な言葉でよい。Claude が各スキルの description（いつ使うかを書いた説明文）を読んで、合うスキルを選ぶ。名前を指定して呼ぶときは `/daily-schedule` のように書く。

| 場面 | スキル | 何をしてくれるか | こう頼む |
|---|---|---|---|
| 朝 | `/daily-schedule` | 今日（または明日）の予定・タスク・前日の持ち越しから、15分刻みの工程表を作る。準備資料が無い会議も教えてくれる | 「今日の工程表をつくって」 |
| 受信箱 | `/inbox-triage` | メールとチャットで、自分宛てにまだ返していないものを洗い出し、優先度をつけて一覧にする | 「返信漏れてない？」 |
| 受信箱 | `/reply-draft` | 受信メールへの返信を下書きする。チャットの返信文も作れる。日程調整は予定の空きから候補を出す（送信・投稿はしない） | 「このメールの返信を下書きして」 |
| 会議 | `/mtg-prep` | 会議の前に、予定・過去の議事録・メール・チャット・手元のメモを集めて準備資料を作る。相手に見せてよい部分と社内メモの2部構成。1on1 の準備にも対応 | 「明日のA社との打ち合わせの準備資料をつくって」 |
| 会議 | `/meeting-notes` | 議事録を Slack／Teams／メールにそのまま貼れる文面にする（送信はしない） | 「さっきの打ち合わせの議事録を出して」 |
| 会議 | `/1on1-writeback` | 1on1 の記録をメンバーごとのファイルに書き戻し、次の1on1につなげる | 「今日のAさんとの1on1を記録して」 |
| 考える | `/kabeuchi` | 仮説や迷いをぶつけると、反論・見落とし・第3の道を出して、最後に判断を3行でまとめる。決めたことは判断の記録に残せる | 「この方針で壁打ちしたい」 |
| 調べる | `/company-research` | 取引先・商談相手・提携先を調べて、会社ごとのカルテを作る・更新する | 「A社のカルテをつくって」 |
| 調べる | `/reading` | 本の要点をつかみ、自分の仕事への実践ガイドにする。読んだ後の振り返りも | 「この本をまとめて」 |
| 調べる | `/clip` | 気になった記事・URLを要約して、タグ付きで保存する | 「これをクリップして」 |
| 発信 | `/write-article` | 自分の文体で、記事・発信文の下書きを書く（投稿は自分で） | 「このテーマで note の記事を書いて」 |
| 発信 | `/eli5` | むずかしい仕組みを、大きな絵と少ない言葉の「しくみ絵本」で説明する | 「◯◯を絵本で説明して」 |
| 夜 | `/daily-log` | 1日の終わりに、やったこと・進行中・明日への持ち越しを日報にまとめる | 「今日の日報をまとめて」 |
| 週末 | `/weekly-report` | その週の日報を束ねて、成果・進捗・課題・判断したこと・来週の注力を週次レポートにする。追っている数字があれば前週と並べる | 「今週の振り返りをつくって」 |
| 片付け | `/downloads-triage` | ダウンロードフォルダを週1回仕分ける（消さずに移動。動かす前に確認） | 「ダウンロードを整理して」 |

1本試すごとに、あなた（Claude Code）は結果をユーザーに見せ、「期待と違ったところ」を聞く。違いの直し方は 6-3 にある。

> 💡 **実運用例**: 朝は「今日の工程表をつくって」、会議の前は「明日の◯◯さんとの打ち合わせの準備資料をつくって」、夜は「今日の日報をまとめて」。この3つが回りだすと、日報に書いた「持ち越し」を翌朝の工程表が拾い、金曜の週次レポートがその週の日報を束ねる、という1本の流れになる。

### 6-3. 自社に合わせる

あなた（Claude Code）はユーザーと次の3点をそろえて、パックを自社で使える状態にする。パックは、どの会社でも使えるように道具を「カレンダー」「メール」「チャット」のような役割で書いてあるので、自社の保存先・道具・基本情報はここで合わせる。

1. **保存先をそろえる**: パックの既定の保存先は、工程表・日報が `work/daily/`、週次レポートが `work/weekly/`、会議の準備資料が `work/mtg/` など（全体は下の図）。第1部で別のフォルダ（例: `work/reports/`）を決めていた場合は、パックの既定に合わせるか、第1部で決めた保存先に統一するかをユーザーに聞き、決めた保存先を `CLAUDE.md` に書く。`CLAUDE.md` に書いた保存先は、パックの既定より優先される
2. **つながっている道具を確かめる**: スキルは、つながっている道具だけを使う。つながっていない道具は黙って飛ばさず、「使えなかった」と書くか、内容を貼るようユーザーに頼む。よく使うのにつながっていない道具があれば、第1部 Step 3 に戻って接続する
3. **最初の2ファイルを置く**: `context/owner/profile.md`（ユーザーのプロフィール・仕事の進め方）と `context/company/overview.md`（会社の概要・事業・用語）。どちらも第3部で充実させるので、ここでは数行でよい。書いてあることが多いほど、スキルの出来が上がる

パックが前提にしているフォルダ構成（無いフォルダはスキルが作る）:

```
context/
  owner/profile.md       自分のプロフィール・価値観・仕事の進め方
  company/overview.md    会社の概要・事業・用語
  company/decisions.md   判断の記録（kabeuchi・daily-log が日付つきで書き足す）
  company/kpi.md         追っている数字（あれば。weekly-report が読む。社外に出さない）
  clients/<相手先>.md     取引先ごとのカルテ（company-research が作る）
  members/<名前>.md       メンバーごとのファイル（1on1-writeback が書き戻す）
work/
  mtg/  clips/  reading/  content/  research/
  mail/                  返信下書きの控え（残したいときだけ）
  daily/                 工程表・日報・未返信チェック
  weekly/                週次レポート
```

**スキルの中身を直すとき**: 手順や出力が自社に合わない点は、ユーザーの了承を得て、あなた（Claude Code）がそのスキルの `SKILL.md` を直す。同じ失敗をくり返さないための教訓は、そのスキルの Gotchas に1行で書き足す（書き方は 6-4）。

**全スキル共通の約束**（パックに組み込み済み。自社向けに直すときも外さない）:

- メールは下書きまで。送信・転送・予約送信はしない。送信ボタンはユーザー本人が押す
- チャットの投稿も、文面を作るところまで。投稿はユーザー本人がする
- 相手に見せる部分と社内メモを分ける。相手に見せる部分には、金額・社内での評価・社内の段取りを書かない
- パスワード・APIキーなどの認証情報は読まない・書かない
- 「メールアドレスが同じ」というだけで同一人物と決めつけない。迷ったらユーザーに確認する

### 6-4. パックに無い仕事を自作で足す

役割や自社に固有の繰り返し業務のうち、パックに無いものは、自作のスキルにする。**ビルダーで選んだ「自作で足す」の中から、よく使う1〜2個だけを作る。** 最初から全部は作らない。「自作で足す」が（なし）のときは、下の表や役割ごとの候補からユーザーと相談して選ぶか、パックを使い込んでから決める。

役割ごとの候補は [companion/role-contexts/](companion/role-contexts/) の「自作で足す」にある。役割をまたぐ候補は次の表のとおり（作り方の例があるのは `/interview` だけ）。**「汎用」はユーザーへの聞き取りだけで作れる。「要カスタマイズ」は、置換ポイント（自社のCRM・観点リストなど）の中身を先にユーザーに聞いてから作る。**

| スキル | 内容 | 区分 / 置換ポイント |
|---|---|---|
| `/interview` | 仕様・施策・求人要件などを、着手前に質問で深掘りして spec（要件をまとめたメモ）に落とす | 汎用（下の作り方の例） |
| 画像生成（`/img` 等） | 1行の指示で画像を生成し work/ に振り分け | 汎用（画像生成MCPが要る） |
| 商談フィードバック・ナーチャリング系 | 商談議事録の分析、見込み客へのフォロー漏れ通知 | 要カスタマイズ（→自社のCRM/案件管理に置換） |
| 契約レビュー（NDA等） | 受領した契約書を観点リストで判定し修正案を出す | 要カスタマイズ（→自社の観点リストに置換） |
| KPI日次決算 | 日々の数字を集計しダッシュボード/通知 | 要カスタマイズ（→自社の指標・データ源に置換） |
| テスト設計系 | 仕様書からテスト観点・テストケースを生成 | 業種依存（QA/開発業務がある会社向け） |

#### 自作スキルの作り方（設計原則）

1スキル＝1フォルダで、`.claude/skills/{名前}/SKILL.md` に以下を含める。パックのスキルも同じ形なので、迷ったらパックの `SKILL.md` を開いて真似する。

- **frontmatter**: `name`（スキル名）と `description`（いつ使うか・どんな言葉で頼まれるか）。description でスキルが自動で選ばれるので、CLAUDE.md にトリガー一覧は作らない。重い判断が要るスキルだけ、`model`（opus 等）を指定してもよい
- **手順**: 番号付きステップで実行順を明示
- **並列実行の指示**: 独立した情報収集は「並列で実行」と明記（速度が大きく上がる）
- **出力形式**: テンプレートで出力フォーマットを定義
- **出力先**: 保存先パスを明示（例 `work/research/`）
- **Gotchas（過去にハマったケース）**: ★重要。実際にやらかした失敗を「1行の教訓＋具体ケース＋日付/出典」で書き溜める。スキル内で最も役立つセクションになる（Anthropicのスキル運用で「Gotchasは最高シグナルのcontent」と提唱されている）。最初は空でよく、事故が起きるたびに足す
- **実運用の例を1行添える**: 「実際こう使う」を1行入れると、ユーザーが自分ごとにしやすい

```markdown
## Gotchas（過去にハマったケース）
1. **{1行で言える教訓}**: {何が起きたか／どう判定するか}（{日付・出典}）
```

#### 作り方の例：`/interview`（着手前ヒアリング → spec）

人事・採用、開発・QA、デザイナーの「自作で足す」の筆頭。`.claude/skills/interview/SKILL.md` として作る。

```markdown
---
name: interview
description: 仕様・施策・記事構成・求人要件などを、着手前に質問で深掘りして spec にまとめたいとき。「着手前に要件を固めたい」「インタビューして」「要件を整理して」で発火
---
# インタビュー（着手前ヒアリング）

実装・作成に入る前に、AskUserQuestion（選択肢を出して選んでもらう質問形式）で要件を固める。

1. お題に対し、決めるべき論点を3〜5個に分解
2. 1論点ずつ選択肢を提示して選んでもらう（推測で埋めない）
3. 固まった要件を work/specs/{お題}-spec.md に書き出す
4. 「このspecで別セッションで実装/作成できる状態か」を最後に確認

## Gotchas
（事故が起きたらここに追記）
```

> 💡 **実運用例**: 求人票を書く前に「このポジションの要件を固めたいからインタビューして」と頼む。必須／歓迎要件・評価軸を選択肢で詰めてから書くので、手戻りが減る。

### メモリ（近代化）— `/agent-memory` は不要

> ※ 旧バージョンの本書には `/agent-memory` という専用スキルがありましたが、**廃止しました**。

会話中に「覚えておいて」と言われたら、Claude Code 標準のメモリシステムに保存する。仕組み：

- 保存先は `~/.claude/projects/{プロジェクトパス}/memory/`。`MEMORY.md` が索引、各記憶は個別の `.md` ファイル
- 保存するのは**非自明な気づき・フィードバック・方針**だけ（type: user / feedback / project / reference で分類）
- **寿命の長い「事業の事実」は memory/ ではなく context/ に書く**（メモリは最終手段）。「顧客や事業の事実 → context/」「AIへの指示・修正 → memory/」と振り分ける
- 既存の記憶と重複しないか確認し、重複は更新する

専用コマンドを作らなくても、この振り分けルールを CLAUDE.md に書いておけば「覚えておいて」で機能する。

### 完了条件

- AI秘書スキルパックの15本が `.claude/skills/` に、調査係が `.claude/agents/` に入っている（プラグインで入れた場合は、`/plugin` の画面で有効になっている）
- 同じ名前の旧スキル・旧コマンドが残っていない（`.claude/_archive/` へ移した）
- 「まず試す」のスキル（`/daily-schedule`・`/mtg-prep` ＋役割のおすすめ）を実際に頼んで動かし、ユーザーが結果を確認した
- 保存先が、パックの既定か `CLAUDE.md` に書いた場所でそろっている
- 自作スキルを足した場合は、description が「いつ起動するか」を表す書き方になっていて、Gotchas の枠がある（CLAUDE.md にトリガー一覧は作らない）
- メモリの振り分けルールが CLAUDE.md に書かれている

## Step 8：サブエージェント ＆ Agent Team【発展】

### 委任の原則（まずこれ）

1つのセッションで全部やると、コンテキストが汚れて精度が落ちる。**重い作業は別のエージェントに委任して、本体のコンテキストを守る**。

- **委任する基準**: 調査・リサーチ／2つ以上の独立したタスク／3回以上の検索／スキル内の重い処理
- 委任したら**結果を信頼し、自分でやり直さない**（やり直すと委任の意味がない）
- 独立した複数タスクは**並列で投げる**（速度が大きく上がる）

### 単発エージェント vs Agent Team

- **単発エージェント**（`Agent` ツール）: Web調査・テキスト整形・議事録要約・データ取得など、1つの仕事を投げて結果を受け取る。**パックの調査係（researcher）がこれにあたる。** 調査係は、手元のファイル・Web・つながっている道具を横断して調べ、要点と出典だけを返す（道具は読むだけで、送信・投稿・予定の作成はしない）。`/company-research` は、調べものをこの調査係に任せる作りになっている。ほかに「調査係に任せて◯◯を調べて」と直接頼むこともできる。自分で別の係を定義するときは、`.claude/agents/{名前}.md` に `name:` と `description:`（任意で `model:`）を書く
- **Agent Team**: 複数の役割が分担して1つの成果物を作る。品質と深さが要る仕事向け。**役割別のチームテンプレ（営業=提案書／開発QA=テスト設計 など）は [companion/role-contexts/](companion/role-contexts/) にある**

### Agent Teamテンプレート

**初回は、パックの調査係に調べものを1つ任せるところから始める。** Agent Team は、受講者の役割テンプレ（[companion/role-contexts/](companion/role-contexts/) の「Agent Team テンプレ」）を1つ選んで作る。下記は横断テンプレ（記事）と、役割テンプレの一覧。

#### テンプレA：記事執筆チーム（`.claude/agents/` ＋ 起動スキル）

パックの `/write-article` は、1つのAIが最初から最後まで書く版。深さと品質が要る記事は、この編成（複数のAIが調査・構成・執筆・レビューを分担）に任せる。

```
リサーチャーA（テーゼ→アンチテーゼ→ジンテーゼで論点を立体化）─┐
リサーチャーB（事実・統計・事例を収集）                      ─┼→ 構成設計 → 編集長レビュー → ライター → 編集長 最終レビュー

```
各リサーチャーは並列実行し、結果を work/content/articles/ に出力。構成→レビュー→執筆→最終レビューの順で品質を上げる。

## Step 7：定期自動実行（Scheduled Tasks）【発展】

スキルを「手で打つ」から「自動で走る」に進化させる工程。**朝起きたら工程表ができている／夜には日報がまとまっている**という、AI秘書が"勝手に動く"体験の核。

### 仕組み

- 決まった時刻（cron＝定刻に自動実行する仕組み）に、決まったスキル/プロンプトを自動実行するよう登録する
- 登録は **`/schedule` コマンド**（または利用環境のスケジュール機能）で行う。まず使える手段をユーザー環境で確認してから案内する
- 登録時は「**時刻（cron）＋実行するスキル＋結果の通知先**」を指定する（例: 毎朝8時に `/daily-schedule` を実行して結果をSlackに通知）
- 実行形態は2種類：**クラウドのルーティン**（PCを開いていなくても走る）と、**ローカルのスケジュールタスク**（自分のPCで指定時刻に走る）。環境に合う方を選ぶ

### スターターセット（まずこの3つ）

| タイミング | 実行する内容 |
|---|---|
| 平日 朝 | `/daily-schedule`（工程表）と `/inbox-triage`（未返信の洗い出し） |
| 平日 夜 | `/daily-log`（日報） |
| 金曜 夕方 | `/weekly-report`（週次レポート） |

夜の日報に書いた「持ち越し」を翌朝の工程表が拾い、金曜の週次レポートがその週の日報を束ねる。定期実行のあいだは誰にも質問できないので、パックのスキルは確認が必要な点を成果物の「要確認」に書き残す。朝のうちに「要確認」に目を通すよう、ユーザーに伝える。

慣れたら「週次のフォローアップ漏れチェック」「月初のメモリ棚卸し」なども足せる。

### 設計のコツ

- 各定期タスクも、スキルと同じく **手順＋出力先＋Gotchas** を持つ小さな指示書として書く
- 実行結果は通知（Slack DM等）かファイル出力で受け取れるようにする

### Gotchas（定期実行で注意すること）

- **依存データの有無**: 朝タスクが前夜のログに依存する場合、前夜タスクが失敗すると朝も崩れる。各タスクは「データが無くても落ちない」作りにする
- **多重起動**: 同じタスクを二重登録しない。登録済み一覧を先に確認する
- **静かな失敗**: 自動実行は失敗に気づきにくい。「N時間以上実行されていないタスクを検知して通知」する見張りタスクを1本入れておくと安全

### 完了条件

- スターターセットのうち最低1つ（推奨: `/daily-schedule`）が登録され、テスト実行で動く
- 実行結果の受け取り方（通知 or ファイル）が決まっている

## Step 10：Git管理を設定する【発展・任意・スキップ可】

### ヒアリング項目

- Gitを使ったことがあるか（初めて / 聞いたことはある / 使ったことがある）
- 複数PC（会社・自宅）で同じAI秘書環境を使いたいか
- チームでAI秘書の設定を共有する予定があるか

### やる vs やらない（判断ガイド）

| 観点 | Git管理する | しない |
| --- | --- | --- |
| 変更履歴 | 全変更が記録され、壊しても戻せる | 履歴なし。壊したら手動 |
| バックアップ | GitHubにpushすればPC故障でも復元可 | 手動バックアップが必要 |
| 複数端末の同期 | `git pull` で別PCに即再現 | フォルダごとコピー |
| 学習コスト | commit/push の理解が要る（Hooksで自動化すればほぼゼロ） | 追加学習なし |
| セキュリティ | .gitignore を誤ると機密漏洩リスク | 流出リスクが発生しない |

**やるべき人**: 複数PCで作業／壊しても自力で直す自信がない（巻き戻しが安全網）／チームで共有したい人。
**スキップでOK**: まず最小構成で試したい／1台でしか使わない／Gitに時間を使いたくない人。**後からいつでも追加できる。**

### 実行内容（やる場合）

1. プロジェクトフォルダを `git init`
2. `.gitignore` を作成（最低限: `.env` / `*.key` / `credentials/` / `CLAUDE.local.md`（個人設定）/ `context/owner/`（個人情報を含む場合））
3. 初回コミット
4. ユーザーの許可を得て、GitHubに**プライベート**リポジトリを作成しpush

### 発展: git安全装備（自信が付いたら）

事故防止を仕込んでおくと安心：

- **pre-commit フック**でAPIキー・秘密鍵（`AKIA…` / `BEGIN … PRIVATE KEY` / トークン類）をスキャンし、混入時はコミットを止める
- **Bash実行前バリデーション**（Step 4のHook）で破壊系コマンドをブロック
- これらは独立に動き、1つが破られても他が止める多層防御になる

### スキップする場合

最低限、プロジェクトフォルダを定期的にGoogle Drive等へコピーしてバックアップする。**ユーザーが「スキップ」を選んだら、このStepは飛ばして最終確認へ。**

4. 画面に表示する（保存先は第2部でスキルパック版に置き換えるときに決める）
